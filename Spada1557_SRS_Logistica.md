## 1. ВВЕДЕНИЕ

### 1.1. Назначение

Настоящий документ Software Requirements Specification (SRS) описывает функциональные и нефункциональные требования к информационной системе управления транспортной логистикой «LogiTrack».

Документ предназначен для:

- заказчиков (руководство транспортной компании);
- разработчиков и тестировщиков;
- аналитиков и проектировщиков БД.

Документ является эталоном для проектирования, разработки, тестирования и приёмки системы. Все изменения требований должны фиксироваться в новых версиях данного SRS.

### 1.2. Область действия

Система «LogiTrack» предназначена для автоматизации процессов транспортной и складской логистики средней транспортной компании (50–200 единиц транспорта, 2–5 складов).

Система покрывает:

- приём и обработку заявок на грузоперевозки (FTL/LTL);
- планирование маршрутов и назначение водителей/ТС;
- трекинг грузов в реальном времени;
- складской учёт (приёмка, размещение, отгрузка);
- расчёт тарифов и формирование счетов;
- работу с клиентами, перевозчиками и водителями;
- аналитику и отчётность (KPI логистики).

Система НЕ покрывает:

- бухгалтерский и налоговый учёт в полном объёме (интеграция с 1С по API);
- таможенное оформление (только хранение сканов документов);
- управление производством и закупками.

Наименование продукта: «LogiTrack».
Цели внедрения: сократить время обработки заказа на 30%, снизить порожний пробег на 15%, исключить потерю грузов и обеспечить прозрачный трекинг для клиентов.

### 1.3. Определения и сокращения

Глоссарий терминов:

| Термин / Сокращение | Определение |
|---|---|
| SRS | Software Requirements Specification — спецификация требований к ПО (IEEE 830) |
| FTL | Full Truck Load — полная загрузка транспортного средства одним заказом |
| LTL | Less Than Truck Load — сборная перевозка, несколько заказов в одном ТС |
| ТС | Транспортное средство (грузовой автомобиль) |
| Заказ | Заявка клиента на перевозку груза из точки А в точку Б |
| Рейс | Выполняемая перевозка: ТС + водитель + маршрут + заказы |
| Трек-номер | Уникальный идентификатор заказа для отслеживания |
| KPI | Ключевые показатели эффективности (срок доставки, % вовремя, стоимость/км) |
| Роль | Набор прав доступа: Администратор, Логист, Водитель, Кладовщик, Клиент |
| WMS | Warehouse Management System — подсистема складского учёта |

## 2. ОБЩЕЕ ОПИСАНИЕ

### 2.1. Перспектива продукта

«LogiTrack» — новая автономная веб-система (клиент-серверная архитектура), заменяющая ручной учёт в Excel и мессенджерах.

Взаимосвязь с другими системами:

- **1С:Бухгалтерия** — выгрузка счетов и актов (REST API / CSV);
- **Картографический сервис** (Yandex Maps / OSM) — построение маршрутов, расчёт расстояний;
- **SMS/Email-шлюз** — уведомления клиентов и водителей;
- **GPS-трекеры / мобильное приложение водителя** — передача координат каждые 60 сек;
- **СУБД PostgreSQL 16** — хранение данных системы.

Архитектура: Backend (REST API) + Web-клиент (SPA) + Мобильное приложение водителя (трекинг, статусы). Развёртывание — Docker Compose (web, db, api).

Пользователи работают через браузер (логист, администратор, клиент, кладовщик) и мобильное приложение (водитель).

### 2.2. Функции продукта

Список основных функций:

1. Управление пользователями и ролями (RBAC).
2. Ведение справочников: клиенты, водители, ТС, склады, тарифы.
3. Создание и обработка заказов на перевозку (статусы: Новый → Принят → Назначен → В пути → Доставлен → Закрыт/Отменён).
4. Автоматический расчёт стоимости по тарифам (вес, объём, расстояние, тип груза).
5. Планирование рейсов: группировка заказов (LTL), назначение ТС и водителя, оптимизация маршрута.
6. Трекинг груза по трек-номеру для клиента (карта + статусы).
7. Складской учёт: приёмка, размещение по ячейкам, инвентаризация, отгрузка.
8. Уведомления (email/SMS/push) о смене статуса заказа.
9. Формирование счетов, актов, ТТН (печать PDF).
10. Отчёты и дашборды: KPI, загруженность автопарка, прибыльность рейсов.

### 2.3. Характеристики целевых пользователей

Описание целевых пользователей:

| Пользователь | Описание | Технические навыки | Права |
|---|---|---|---|
| Администратор | ИТ-сотрудник, настраивает систему | Высокие | Полный доступ, пользователи, тарифы |
| Логист (диспетчер) | Планирует рейсы, обрабатывает заказы, 10–20 чел. | Средние (браузер, Excel) | Заказы, рейсы, справочники, отчёты |
| Водитель | Исполнитель перевозки, 50–200 чел. | Базовые (смартфон) | Свои рейсы, смена статуса, геопозиция |
| Кладовщик | Приёмка/отгрузка на складе | Базовые | Складские операции своего склада |
| Клиент | Заказчик перевозки (B2B) | Средние | Создание заказов, трекинг, счета, история |

Ожидаемая нагрузка: до 100 одновременных пользователей web, до 200 мобильных клиентов.

### 2.4. Ограничения

Технические, бюджетные, временные:

- Технологический стек: Backend — Python/Java + REST, Frontend — SPA, СУБД — PostgreSQL 16, развёртывание — Docker.
- Поддержка браузеров: Chrome/Edge/Firefox последних 2 версий; мобильное приложение — Android 10+.
- Время отклика web-интерфейса: не более 2 сек при 100 пользователях.
- Безопасность: хеширование паролей (bcrypt), JWT-сессии, HTTPS, аудит действий.
- Доступность: 99% в рабочее время (8:00–22:00), RPO ≤ 24 ч, RTO ≤ 4 ч (ежедневный бэкап БД).
- Бюджет и сроки учебного проекта: MVP за 3 месяца силами команды 3–4 человека.
- Соответствие ФЗ-152 «О персональных данных», хранение ПДн на территории РФ.
- Интерфейс — русскоязычный.

## 3. СПЕЦИФИЧЕСКИЕ ТРЕБОВАНИЯ

### 3.1. Функциональные требования

**FR-001: Регистрация и аутентификация пользователей**

Система должна позволять регистрацию клиентов по email и вход по логину/паролю с восстановлением пароля.
Приоритет: Высокий

**FR-002: Управление ролями и правами доступа (RBAC)**

Система должна ограничивать доступ к функциям по ролям: Администратор, Логист, Водитель, Кладовщик, Клиент.
Приоритет: Высокий

**FR-003: Ведение справочника клиентов**

Система должна хранить: наименование, ИНН, контактное лицо, телефон, email, адрес, историю заказов.
Приоритет: Высокий

**FR-004: Ведение справочника ТС и водителей**

Система должна хранить для ТС: госномер, марку, грузоподъёмность (т), объём (м³), статус (Свободен/В рейсе/Ремонт); для водителя: ФИО, телефон, ВУ, закреплённое ТС, статус.
Приоритет: Высокий

**FR-005: Создание заказа на перевозку**

Клиент/логист должен иметь возможность создать заказ: отправитель, получатель, адреса, дата готовности, вес, объём, тип груза, требования (рефрижератор, хрупкое). Система присваивает трек-номер формата `LT-YYYY-XXXXXX`.
Приоритет: Высокий

**FR-006: Расчёт стоимости перевозки**

Система должна автоматически рассчитывать стоимость по формуле: `тариф(руб/км) × расстояние + надбавки (вес/тип/срочность)`. Расстояние — по картографическому API.
Приоритет: Высокий

**FR-007: Планирование рейса и назначение ресурсов**

Логист должен иметь возможность объединять заказы в рейс (LTL с контролем перегруза по весу/объёму), назначать ТС и водителя, строить оптимальный порядок точек маршрута.
Приоритет: Высокий

**FR-008: Смена статусов заказа/рейса**

Система должна поддерживать жизненный цикл: Новый → Принят → Назначен → В пути → Доставлен → Закрыт, а также Отменён. Смена статуса водителем — из мобильного приложения в 1 клик.
Приоритет: Высокий

**FR-009: Трекинг груза клиентом**

Клиент должен иметь возможность по трек-номеру видеть текущий статус, местоположение на карте и прогноз прибытия (ETA).
Приоритет: Средний

**FR-010: Складские операции (приёмка/размещение/отгрузка)**

Кладовщик должен иметь возможность фиксировать приёмку груза, размещение по ячейкам (зона-стеллаж-ячейка), отгрузку в рейс и инвентаризацию.
Приоритет: Средний

**FR-011: Уведомления о статусах**

Система должна отправлять email/SMS/push при смене статуса заказа (Принят, В пути, Доставлен) и за 2 часа до прибытия.
Приоритет: Средний

**FR-012: Формирование счетов, актов и ТТН**

Система должна генерировать печатные формы счёта, акта выполненных работ и ТТН в PDF по шаблону.
Приоритет: Средний

**FR-013: Дашборд и отчёты KPI**

Система должна формировать отчёты: % доставок вовремя, средний срок, стоимость/км, загруженность автопарка, прибыль по рейсам, с фильтрами по периоду/клиенту/водителю и экспортом в Excel.
Приоритет: Низкий

**FR-014: Приём GPS-координат от водителей**

Система должна принимать координаты от мобильного приложения каждые 60 сек и хранить трек рейса не менее 90 дней.
Приоритет: Средний

### 3.2. Нефункциональные требования

**NFR-001: Производительность web-интерфейса**

Список заказов из 10 000 записей должен открываться не более чем за 2 сек при 100 одновременных пользователях.
Метрика: Замер времени отклика API (p95 ≤ 2 сек, нагрузочный тест JMeter/k6).

**NFR-002: Доступность**

Система должна быть доступна 99% времени в окно 8:00–22:00.
Метрика: Мониторинг uptime (Prometheus/Uptime), журнал простоев.

**NFR-003: Надёжность хранения данных**

Ежедневный автоматический бэкап БД, RPO ≤ 24 ч, RTO ≤ 4 ч.
Метрика: Проверка восстановления из бэкапа 1 раз в месяц, лог бэкапов.

**NFR-004: Безопасность**

Пароли — только в виде bcrypt-хэша, все соединения — HTTPS, защита от SQL-инъекций/XSS, аудит входа и смены статусов.
Метрика: Отсутствие критических уязвимостей по OWASP Top 10 (сканер + ревью).

**NFR-005: Удобство использования (Usability)**

Новый логист должен создавать заказ без обучения не более чем за 5 минут; интерфейс — на русском языке.
Метрика: Юзабилити-тест на 5 пользователях, ≥ 80% успешных сценариев без подсказок.

**NFR-006: Масштабируемость**

Система должна масштабироваться до 500 ТС и 500 000 заказов/год без изменения архитектуры (горизонтальное масштабирование API, индексы БД).
Метрика: Нагрузочный тест с 500 RPS, деградация p95 не более 20%.

**NFR-007: Совместимость**

Web-клиент — Chrome/Edge/Firefox последних 2 версий; API — REST/JSON с версионированием `/api/v1`.
Метрика: Матрица кросс-браузерного тестирования, Postman-коллекция API.

## 4. ПРИЛОЖЕНИЯ

Диаграммы, mockups, etc.:

1. **Диаграмма вариантов использования (Use Case):** акторы Администратор, Логист, Водитель, Кладовщик, Клиент; прецеденты — из раздела 2.2.
2. **BPMN процесса «Обработка заказа»:** Заявка → Расчёт → Согласование → Назначение рейса → Погрузка → В пути (трекинг) → Выгрузка → Закрытие/Оплата.
3. **ER-диаграмма БД (упрощённо):** Client(1)—(*)Order(* )—(*)Trip; Driver(1)—(*)Trip; Vehicle(1)—(*)Trip; Warehouse(1)—(*)Cell(1)—(*)StockMove; Order(1)—(*)StatusHistory, (*)Notification.
4. **Макеты экранов (mockups):**
   - Список заказов с фильтрами и статусами;
   - Карточка заказа с расчётом стоимости;
   - Планировщик рейсов (drag-and-drop заказов в ТС);
   - Трекинг для клиента (карта + таймлайн);
   - Склад: приёмка и адресное хранение.
5. **Шаблоны печатных форм:** счёт, акт, ТТН.
6. **Пример трек-номера:** `LT-2026-000421`.
7. **Пример расчёта тарифа:** Москва–Казань 820 км × 65 руб/км = 53 300 руб + надбавка за рефрижератор 10% = 58 630 руб.
